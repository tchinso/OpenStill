## 1. 인계받은 작업자의 시작점

이 문서는 다른 계정/새 채팅에서 구현을 이어가기 위한 계획이다. 현재 채팅에서 사용자에게 승인받은 작업은 **조사·검사·계획서 작성**이며, 운영 코드 수정은 아직 하지 않았다. 이후 사용자가 이 계획의 실행을 요청하면 아래 범위를 구현한다.

목표는 다음 두 가지다.

1. 기존 로컬 JSON 내보내기·불러오기에서 확인된 원본 덮어쓰기, 본문 누락, 지문 오판을 수정한다.
2. 같은 백업 형식을 사용하는 **Koofr 내보내기·불러오기와 주기 자동 백업**을 추가한다. 자동 백업은 앞서 사용자가 요청했던 범위를 포함하며 기본값은 꺼짐으로 한다.

Dropbox, Google Drive, OneDrive, B2, MEGA S4, 다른 WebDAV 사업자를 추가하는 것은 이번 범위에 넣지 않는다. Koofr를 선택했으므로 서비스 재선정 조사를 반복할 필요가 없다.

개인 프로필·실제 사용자 저장소에서 삭제·덮어쓰기 검사를 하지 않는다. 합성 자료와 임시 브라우저 프로필을 사용한다. 실제 사용자 백업이 제공되면 원본 파일을 보존한 채 사본으로 검사한다.

아래 배치는 구현자의 취향으로 바꾸지 않는다.

구현 기준:

- 키 입력 버튼의 권장 문구는 “Koofr 설정”이다. 설정창의 인증 필드는 “이메일”, “앱 비밀번호”로 표시한다. Koofr에는 이 방식의 인증정보를 사용하며, 일반 계정 비밀번호나 개발자 App Key를 요구하지 않는다.
- #runtimeOwnership은 정리 대상이 없으면 숨겨지는 기존 버튼이다. Koofr 설정 버튼이 그 버튼의 표시 여부에 종속되지 않게 한다.
- 상단의 권장 순서는 로컬 내보내기 → 로컬 불러오기 → 복구함 → Koofr로 내보내기 → Koofr에서 불러오기다. 기존 진행 표시를 보존한다.
- 초기 HTML 상태는 Koofr 전송 버튼 hidden이다. 등록 상태를 읽기 전에 잠깐 노출되지 않게 한다.
- “등록됨”과 “현재 통신 가능”은 별개다. 자격정보가 저장된 뒤 네트워크 오류/인증 만료가 발생해도 버튼을 갑자기 숨기지 말고 오류와 재설정 경로를 제공한다.
- 등록 해제 시 전송 버튼을 숨기고 자동 백업을 끈다. **등록 해제만으로 원격 백업을 삭제하지 않는다.**
- 설정창에 연결 확인, 저장, 정보 삭제, 자동 백업 주기, 마지막 성공/실패 상태를 모은다. 별도 대형 클라우드 관리 화면을 만들 필요는 없다.
- 기존 데이터 안내 문구 “이 브라우저에만 저장됩니다”는 Koofr 선택 백업을 정확히 설명하도록 수정한다.

현재 위치: dashboard.html 약 13–20행, 85행; dashboard.js 약 3069행의 recoveryButton 삽입부. 행 번호는 후속 변경 전에 다시 확인한다.

## 5. 로컬 백업에서 수정할 문제

### L1. 복구 원본의 같은 ID·다른 내용 덮어쓰기 — 우선순위 높음

**재현된 현상**

- 서로 다른 프로필의 정상 구형 데이터 마이그레이션을 실행한다.
- 프로필 A와 B의 첫 번째 원본은 모두 legacy-container:0이라는 ID로 내보내진다.
- A 백업을 가져온 뒤 B 백업을 가져오면 복구함의 A 원문이 B 원문으로 대체된다.
- 정상 추적 레코드는 둘 다 남더라도, 과거 원본 증거는 하나가 사라진다.
- UUID가 우연히 충돌한 문제가 아니다. 고정 ID와 순번을 쓰는 실제 경로의 문제다.

**수정 위치**

- service-worker.js: loadMonitorRepository의 legacy-container / legacy-invalid-* 생성
- export-session.js: legacy-container 분할, recovery.id를 staging 키로 사용하는 부분
- import-session.js: _openStillRecovery 저장과 _openStillRecoveryFile 조립 완료 저장
- record-store.js: commit의 복구·삭제 원본 저장, snapshotPatches의 손상 원문 보관
- preserveImportRaw, 중단/폐기, export 중 손상 원본 보관을 포함한 **모든 recovery writer**

**설계**

1. 원본이 갖고 있던 ID와 현재 저장소에서 쓰는 보관 ID를 분리한다. 예: local id, sourceOriginalId, 원본 내용 지문. 필드명은 구현자가 정하되 역할은 분명히 한다.
2. 같은 원본 ID·같은 내용은 재사용하고, 같은 ID·다른 내용은 둘 다 보존한다.
3. 백업 반복 가져오기나 실패 후 재시도 때 원본 항목이 끝없이 늘지 않게 한다. 항상 무작위 접미사를 붙이는 해결은 피한다.
4. 비교용 지문에 매번 새로 만든 로컬 보관 시각·표시 ID를 포함하지 않는다. 원래 원문·원래 메타데이터와 로컬 관리 메타데이터를 분리한다.
5. Blob/File은 실제 바이트를 비교한다. JSON.stringify(Blob)은 빈 객체가 되므로 중복 비교에 쓰면 안 된다. 청크로 처리 가능한 파일 지문을 사용하고 이름·타입 등 메타데이터는 별도 보존한다.
6. IndexedDB에서는 기존 값 확인과 신규 삽입을 같은 readwrite 트랜잭션에서 처리한다. 지문 계산은 트랜잭션 전에 한다. 세션별 JS 큐만으로 다른 세션·Worker의 동시 저장이 안전해지지는 않는다.
7. 추적 삭제와 삭제 원본 보관의 기존 원자성을 깨뜨리지 않는다. 안전 보관 helper를 추가한다면 commit 내부 patch 경로에서도 사용 가능해야 한다.
8. 저장 키와 entry.id가 달라질 경우 모든 export/UI/복원 조회 경로를 맞춘다. recovery.id만으로 staging 키를 다시 만들어 두 항목을 합쳐버리지 않게 한다.
9. 정상 기존 복구 원본을 일괄 재명명하는 대규모 마이그레이션은 피한다. 필요한 부가 필드는 점진적으로 채우되 기존 raw는 보존한다.
10. 이미 덮어써져 사라진 원문은 원래 백업 파일이 있어야 회수 가능하다.

**완료 기준**

- 실제 생성 경로의 A/B legacy 백업을 합친 뒤 A·B 원문 모두 남는다.
- 같은 백업을 3번 가져와도 같은 원본 수는 늘지 않는다.
- 동시 가져오기에서도 두 원문이 남는다.
- 같은 이름·크기·타입이지만 바이트가 다른 Blob 두 개가 모두 남는다.
- 정상 추적의 기존 ID 충돌 처리와 복구함의 표시·복원이 깨지지 않는다.

### L2. 두 번째 이후 변경 이력 원문을 내보내기에서 생략 — 우선순위 높음

**재현된 현상**

- history에 서로 다른 본문 3개를 가진 추적을 준비한다.
- 백업을 새 저장소에 가져오면 첫 번째 본문만 남고, 두 번째와 세 번째는 빈 문자열 및 contentOmitted:true가 된다.
- 동일 백업을 원래 저장소에 다시 가져오면 원본과 내용이 달라진 것으로 판정하여 imported:1, conflicts:1의 추가 추적이 생긴다.
- 현재 tests/service-worker-import.test.js의 “history timestamp-only export explicitly marks omitted content”가 이 생략을 의도적으로 기대한다.

**수정 위치와 방법**

- service-worker.js: exportHistoryEntryForTransfer / exportMonitorRecordForTransfer
- export-session.js: 변환된 추적에서 snapshot 참조 수집하는 부분
- tests/service-worker-import.test.js와 이력 UI 검사

1. 이미 저장된 history 항목과 snapshot을 그대로 내보낸다. 내보내기만을 위한 추가 축약을 제거한다.
2. 공용 스냅샷은 기존 v5 방식으로 한 번만 내보낸다.
3. 기존 이력 저장 상한 3개와 정규화의 정상 제한은 임의로 늘리지 않는다.
4. 옛 백업에 이미 contentOmitted:true로 기록된 항목은 그대로 받아들이고 “원문 생략” 표시를 유지한다. 생략을 실제 빈 관측값으로 바꾸거나 내용을 추정하지 않는다.
5. 중복 판정을 무조건 느슨하게 만들어 추가 추적을 숨기는 식으로 해결하지 않는다. 보존할 내용을 정확히 내보내 원본과의 일치를 회복한다.

**완료 기준**

- 현재 스냅샷, 변경 전/후 값, 이력 3개, 실행 이력, 이름/URL/locator/라벨/설정/읽음 상태가 백업 왕복 후 일치한다.
- 같은 백업을 원래 저장소에 다시 가져오면 새 추적/충돌이 생기지 않는다.
- 옛 생략형 백업도 정상 처리되고 UI가 생략과 빈 값을 구분한다.

### L3. 폐기한 준비 자료의 스냅샷 본문이 백업에서 누락 — 우선순위 높음

**재현된 현상**

- 빈 저장소에서 스냅샷이 있는 추적을 가져오기 준비 단계까지만 저장한다.
- abortImportSession({ discard: true })로 “준비 작업 폐기”를 실행한다.
- 복구 원본은 raw.monitor에 packed snapshot 참조를 갖는 형태로 남는다.
- 이어 내보내면 normalCount:0, snapshotCount:0, originalCount:1인데 원본 안에는 $snapshot 참조가 남는다.
- 새 저장소로 가져온 뒤 해당 monitor를 unpack하면 “스냅샷 지문이 일치하지 않습니다”가 발생한다.

**수정 설계**

1. 복구 원본의 **내용 자체를 펼쳐 바꾸는 것보다**, 원문을 그대로 보존하고 필요한 snapshot 의존성을 별도 _openStillSnapshot 레코드로 함께 내보내는 방식을 우선한다.
2. 의존성 수집 대상은 정상 추적뿐 아니라 복구 envelope.record, prepared wrapper.monitor, 버전 배열, pending native/import 자료까지 포함한다. 실제 생성되는 wrapper 종류를 열거해 검사한다.
3. 현재 snapshot / lastErrorSnapshot / lastChange.previous·current / history[*].snapshot을 모두 수집한다. 공유 참조는 중복 제거한다.
4. 알려진 wrapper를 처리하는 helper로 추적 후보를 구분한다. 임의 JSON의 모든 객체를 무조건 normalizeMonitor에 넣지 않는다. 알 수 없는 필드와 손상 원문은 그대로 보존한다.
5. 정상 추적이 요구하는 본문을 검증하지 못하면 정상 백업 완료로 처리하지 않는다. 복구 원본 자체가 원래 손상·누락 참조를 가진 경우는 그 증거·진단을 보존하면서 다른 정상 자료의 내보내기를 막지 않는다.
6. 폐기된 prepared wrapper를 다시 추적으로 회수할 경로도 점검한다. 현재 restoreRecoveryRecord는 raw.record를 특별 처리하고, 복구 UI의 복원 버튼은 주로 trash에만 제공한다. 최소 요구는 외부 백업 이후에도 원문과 의존성이 남는 것이며, 복원 버튼을 제공한다면 알려진 prepared 형식을 명시적으로 해석한다.
7. 기존 원본 Blob/File의 이름·타입 등 메타데이터가 빠지지 않도록 _openStillRecoveryFile 호환 필드도 점검한다.
8. 크고 깊은 자료를 한 번에 펼치지 않는다. 16MiB 해석 예산을 넘는 전송 레코드는 기존 fragment 경로를 사용한다.

**완료 기준**

- 준비 → 폐기 → 백업 → 새 저장소 불러오기 후 전체 스냅샷 원문을 회수할 수 있다.
- 같은 자료를 다시 백업·불러오기하는 두 번째 왕복에서도 본문이 유지된다.
- 원래 손상된 참조는 원문·진단이 유지되고 조용히 정상 자료로 바뀌지 않는다.

### L4. 정상 삭제 원본의 지문 불일치 오판 — 우선순위 중간

**재현된 현상**

- 스냅샷이 있는 추적을 삭제해 trash 원본을 만든다.
- 백업을 새 저장소로 가져온 뒤 삭제 원본을 복원한다.
- 본문은 돌아오지만 status가 needs-review가 되고, “원본 레코드 지문이 일치하지 않아 실행을 정지…” 경고가 생긴다.
- 원인은 export-session.js에서 packed envelope.record를 unpack하면서 원래 digest는 그대로 둔 것이다.

**수정 설계**

- L3와 함께 원래 packed record와 원래 digest를 유지하고 참조 snapshot을 별도 전송하면 이 불일치를 피할 수 있다.
- 실제 저장된 record 바이트의 SHA와 원래 digest의 검증을 유지한다.
- 변환이 불가피하다면 원본 record·원본 digest를 증거로 보존하고 전송본의 지문은 따로 정의한다.
- **unpack 후 digest만 다시 계산해서 붙이지 않는다.** 실제로 손상된 원문까지 정상으로 세탁할 수 있다.
- 과거 코드가 이미 펼쳐 저장한 옛 백업은 원래 지문과 맞지 않을 수 있다. 그 백업의 무결성을 소급 증명할 수 없으므로 일괄 경고 제거/자동 활성화하지 않는다.

**완료 기준**

- 정상 삭제 원본의 새 백업 왕복·복원은 내용 일치 및 불필요한 손상 경고 0이다.
- 의도적으로 record 또는 digest를 바꾼 원본은 계속 손상으로 판정된다.
- 정상 증거와 실제 손상 증거가 구분되어 남는다.

## 6. 권장 구현 순서

| 단계 | 작업 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 1 | 위 4건의 의미 있는 회귀 테스트를 먼저 추가 | 현재 코드에서 해당 실패를 재현 |

## 7. Koofr에 대해 확인한 조건

- 무료 10GB, 무료 가입에 카드 불필요.
- WebDAV 연결 주소는 https://app.koofr.net/dav/Koofr 이다.
- 사용자명은 가입 이메일, 비밀번호는 사용자가 생성한 앱 전용 비밀번호다.
- 외부 서비스별 앱 비밀번호 생성은 Koofr의 공식 연결 방식이다. 개발자 OAuth 앱 등록이 필요하지 않다.
- 무료 계정의 외부 접근에는 zip/rar/exe/apk/html 등 파일 형식 제한이 있다. 현재 .json은 제한 예시에 없지만 허용을 완전히 보장하는 목록은 아니다.
- 따라서 **실제 무료 계정의 JSON 백업 업로드·다운로드·재가져오기 시험이 출시 전 확인 사항**이다. 본문에 HTML 스냅샷을 가진 JSON과 분할 파일도 시험한다. 이름만 바꿔 정책을 우회하지 않는다.
- 앱 비밀번호의 고정 만료 기간이나 폴더별 권한 제한은 공식 자료에서 확정하지 못했다. “영구 키”, “OpenStill 폴더만 접근 가능한 키”라고 안내하지 않는다.
- 2년 미로그인 계정은 통지 후 삭제될 수 있다. WebDAV 활동만으로 로그인으로 인정되는지는 확인되지 않았다. 무료 계정의 장기 보관을 보장한다고 쓰지 않는다.
- 일반 WebDAV 저장소를 사용한다. Koofr Vault 연동이나 클라이언트 측 암호화를 이번 첫 구현에 자동 포함하지 않는다.

## 8. Koofr 설정·인증정보 보관

### 설정창

- 이메일, 앱 비밀번호, 연결 확인/저장, 정보 삭제를 제공한다.
- 기본 백업 폴더는 /OpenStill이다. 주소 자체는 Koofr로 고정하고, 임의 외부 서버 주소 입력 기능은 이번 범위에 넣지 않는다.
- 자동 백업 설정을 같은 창에 둔다. 기본 꺼짐, 주기는 1시간/6시간/매일/매주 등 명확한 선택지로 제공하는 것을 권장한다.
- 저장된 비밀번호를 화면에 다시 채워서 노출하지 않는다. 등록 여부와 마스킹된 이메일만 UI에 전달하고, 수정 시 새 값을 받는다.
- 연결 확인은 전용 임시 .json 파일의 생성·조회·삭제까지 확인하되, 자신이 생성한 정확한 경로만 정리한다. 확인 실패 후 일반 사용자 파일을 지우지 않는다.

### 저장 분리

1. 인증정보는 일반 설정과 **별도 chrome.storage.local 키**에 둔다. 예: openStill.koofr.credentials.v1.
2. 기존 normalizeSettings는 입력 객체를 펼쳐 보존하며, export-session은 settings를 통째로 백업한다. 여기에 앱 비밀번호를 넣으면 로컬/클라우드 백업으로 유출된다.
3. 앱 비밀번호·Authorization 헤더·연결 작업의 비밀값은 백업 JSON, import 설정, storage.sync, 로그, 오류 응답, job checkpoint에 넣지 않는다.
4. 기존 TRUSTED_CONTEXTS 접근 설정을 유지한다. Koofr 비밀값은 콘텐츠 스크립트에서 읽을 수 없어야 한다.
5. 새 네트워크 메시지는 sender를 검증한다. 웹페이지나 삽입 스크립트가 임의 URL 요청·백업 삭제를 대리 요청하지 못하게 한다.
6. 원격 자료에 인증정보처럼 보이는 필드가 있더라도 실제 로컬 연결 정보를 교체하지 않는다.
7. 복원으로 자동 백업이 저절로 켜지지 않게 한다. 실행 주기·기기 ID·작업 상태는 이식 가능한 사용자 데이터와 분리한다.
8. Chrome 재시작 후 무인 실행을 위해 로컬 비밀값 보관이 필요하다. 확장 저장소가 완전한 비밀 금고라고 안내하지 않는다. 암호 잠금 기능을 별도로 도입한다면 재시작 후 잠금 해제가 필요하다는 동작까지 정의해야 한다.

## 9. 공통 백업 생성기와 Koofr 전송

### 모듈 경계

권장 분리는 아래와 같다. 파일명은 예시이며 기존 구조를 확인해 최소한으로 나눈다.

| 경계 | 역할 |
| --- | --- |
| 공통 백업 생성기 | 기존 v5 레코드·fragment·part·manifest 생성. DOM·로컬 다운로드 API에 의존하지 않음 |
| 로컬 전송 | 생성된 part를 chrome.downloads로 저장하고 다운로드 완료 뒤 checkpoint |
| Koofr 전송 | 생성된 part를 WebDAV로 PUT/검증하고 원격 확인 뒤 checkpoint |
| 백업 작업 조정 | 상태·중복 실행 방지·중단/재개·예약 |
| 공통 가져오기 | 내려받은 파일도 기존 Worker·staging·복구 진단·중복 판정 경로 사용 |

가능한 새 파일 예: backup-transfer.js, koofr-webdav.js, koofr-backup-jobs.js, backup-worker.js. 실제 추가 파일은 manifest/importScripts/HTML/Worker 및 package-release.ps1의 명시적 파일 목록에 모두 반영한다.

주의:

- dashboard.js의 내보내기 함수를 그대로 주기 타이머에서 호출하는 방식으로 끝내지 않는다.
- 기존 v5 JSON과 세트 무결성 구조를 최대한 유지한다. 새로운 형식 번호는 의미가 달라져 꼭 필요할 때만 올린다.
- 전체 백업을 하나의 거대한 문자열/Blob으로 합치지 않는다. 현재 part 단위와 큰 레코드 조각 처리를 재사용한다.
- 데이터 준비 시점의 일관성을 보장한 뒤 네트워크 전송 중에는 저장 큐를 오래 점유하지 않는다.
- 로컬 다운로드와 Koofr 업로드의 성공 기준을 분리한다. 하나의 대상이 성공했다고 다른 대상의 진행 자료를 정리하지 않는다.

### 원격 폴더 구조 예시

    /OpenStill/
      devices/
        <device-id>/
          backups/
            <backup-id>/
              part-001.json
              part-002.json
              complete.json

- 기기 ID는 프로필별로 생성해 로컬에 유지한다. 복원 파일의 설정에서 복사해 다른 PC와 같아지지 않게 한다.
- 백업 ID는 새 백업마다 생성하되, 중단 후 같은 작업 재개에서는 유지한다.
- 같은 계정의 다른 기기 백업은 조회·선택 복원할 수 있게 하고, 자동 정리는 기본적으로 자기 기기 범위만 다룬다.
- complete.json은 기존 v5 part 자체를 대체하지 않는 작은 목록이다. 예상 파일명·크기·강한 바이트 지문·세트 ID·생성 시각·개수 등을 담는다.
- 기존 backup-integrity 지문은 그대로 검사한다. 별도 SHA-256 바이트 지문과 같은 알고리즘이라고 혼동하지 않는다.
- 원격 목록 파일은 검증되지 않은 입력이다. 내부 파일명과 경로를 믿고 OpenStill 폴더 밖으로 나가면 안 된다.

### 수동 내보내기 순서

1. 연결 상태와 동일 대상 작업의 실행 여부를 확인한다.
2. 변경되지 않는 내보내기 세션을 준비한다.
3. 자기 백업 ID 폴더에 part를 차례로 올린다. 첫 구현은 순차 업로드로 충분하다.
4. 각 파일의 PUT 응답과 다시 읽은 자료의 크기/지문을 검증한 뒤 해당 part checkpoint를 저장한다.
5. 전체 파일이 검증된 뒤 complete.json을 마지막에 게시하고 다시 읽어 확인한다.
6. 이 단계 이후에만 “백업 완료”와 마지막 성공 시각을 기록한다.
7. complete.json이 없거나 읽을 수 없는 폴더는 완료된 백업으로 표시하지 않는다. 원격 서버의 여러 파일이 한 트랜잭션으로 저장된다고 가정하지 않는다.
8. 중간 실패는 기존 정상 백업을 건드리지 않고 재시도 가능 상태로 남긴다.

같은 경로의 latest.json 하나를 계속 덮어쓰는 구조를 기본으로 쓰지 않는다. ETag가 파일 내용의 SHA라고 가정하지 않는다.

### WebDAV 처리

- PROPFIND/Depth:1: 목록과 속성 조회, 207 Multi-Status의 항목별 상태 확인
- MKCOL: 전용 폴더 생성, 이미 존재하는 경우와 권한 실패 구분
- PUT/GET: JSON 파일 저장·검증·다운로드
- DELETE: 사용자가 선택한 백업 또는 자신이 만든 임시 검사 파일 정리
- MOVE 등을 완료 표시의 필수 전제로 삼지 않는다. 사용한다면 Koofr 실동작과 실패 재개를 검증한다.
- 401/403: 무한 재시도하지 않고 인증/권한/제한 오류로 표시
- 429/일시 5xx/네트워크 실패: Retry-After가 있으면 따르고, 제한된 재시도와 backoff 사용
- 507/용량 부족: 백업 실패로 표시하고 이전 정상본 보존
- XML href, 리다이렉트, 파일명은 같은 HTTPS Koofr origin 및 정규화된 전용 폴더 안으로 제한한다. 다른 origin으로 비밀값을 전달하지 않는다.
- 목록 응답·manifest·파일명은 실행할 코드가 아니다. XML/JSON 파싱 후 검증하고 UI에는 텍스트로 표시한다.
- Koofr가 지원하는 quota 속성이 확인될 경우 여유 용량 안내에 활용한다. 속성이 없다고 임의 용량을 추정해 보장하지 않는다.

## 10. Koofr에서 불러오기

1. 완료된 백업 목록에 생성 시각·기기·파일 수·합계 용량을 표시한다.
2. 사용자가 한 백업을 선택한다. “가장 최근 파일 하나”만 읽지 않는다.
3. complete.json과 각 part의 경로·크기·지문·세트 정보를 확인한다.
4. 파일은 part별로 내려받아 기존 import staging과 Worker로 보낸다. 전체 백업을 메모리에 한 번에 모으지 않는다.
5. 기존과 같은 merge 중복/ID 충돌/부분 복구 규칙을 사용한다.
6. 같은 백업을 다시 불러오면 정상 추적·복구 원본이 늘지 않아야 한다.
7. 불완전/손상 원격 백업은 완전한 복원 성공으로 표시하지 않는다. 기존 부분 복구를 제공할 경우 누락·보관 원본·수리·충돌 수를 명확히 보여준다.
8. 복원 중 자동 백업이 중간 상태를 새 정상본으로 올리지 않게 해당 프로필의 백업 실행을 조정한다. 복원 성공 뒤에도 자동 설정을 임의로 켜지 않는다.
9. 불러오기가 실패해도 기존 정상 추적·마지막 정상 클라우드 백업을 유지한다.
10. Koofr에서 내려받은 JSON도 로컬 파일과 동일하게 불신·검증한다. 인증정보·실행 작업·기기 ID를 덮어쓸 수 없게 한다.

## 11. 주기 자동 백업과 느린 업로드

### 예약 정책

- 기본 꺼짐. 사용자가 주기를 설정했을 때만 켠다.
- chrome.alarms로 기한을 관리하고, 시작/업데이트/재시작 때 예약과 진행 상태를 복구한다.
- Chrome/PC가 꺼져 있거나 절전 중일 때 정시 실행을 보장하지 않는다.
- 밀린 예약은 재개 시 한 번으로 합치고 과거 횟수만큼 연속 생성하지 않는다.
- 수동 백업과 자동 백업이 같은 대상에서 동시에 돌지 않게 한다. 이미 수행 중인 백업은 중복 생성하지 않는다.
- 마지막 성공 시각은 원격 완료 세트 검증 후에만 갱신한다.
- 변경 없음 생략은 정상 추적 외에 복구함·설정 변경도 감지할 수 있을 때만 넣는다. repository generation만 보고 생략하면 복구 원본 변경을 빠뜨릴 수 있다.
- 연결 정보 삭제/변경 시 진행 요청 취소·재인증 상태·이전 작업의 잔여 자료를 처리한다.
- 인증 오류와 일시 네트워크 오류를 분리하고, 백그라운드에서 로그인창을 반복해서 띄우지 않는다.

### 실행 수명: 반드시 해결할 기술 항목

현재 로컬 내보내기는 대시보드의 window 타이머가 진행을 돕는다. 이를 그대로 쓰면 대시보드를 닫았을 때 자동 백업을 이어갈 수 없다.

Chrome service worker에는 유휴 종료와 오래 걸리는 fetch 응답에 대한 종료 조건이 있다. 느린 회선에서 32MiB PUT 응답이 30초를 넘는 경우를 반드시 재현한다. checkpoint만 추가하고 실제로는 매번 같은 시간에 끊기는 상태를 완료로 보지 않는다.

권장 검토 경로:

- 공통 직렬화·전송을 담당하는 전용 Worker와 offscreen 실행을 활용할 수 있는지 확인한다.
- 현재 offscreen 문서는 이미 DOM_PARSER/AUDIO_PLAYBACK/WORKERS 이유를 함께 사용한다. 문서는 하나만 존재할 수 있고, 알림음 처리와 수명 정책이 백업을 중단시키지 않는지 검증한다.
- offscreen은 runtime 메시지 중심이며 chrome.storage 등 모든 확장 API를 직접 쓸 수 있는 컨텍스트가 아니다. 필요한 상태는 서비스 워커와 메시지로 교환하거나 공통 IndexedDB 계층을 사용한다.
- 실제 Worker 사용 등 정당한 이유로 구성하고, 알림음 재생·무한 keepalive 같은 편법으로 백그라운드를 상주시켜 해결하지 않는다.
- 기존 선택자 검사·정규식·알림음이 백업과 동시에 동작해도 깨지지 않아야 한다.
- 실행 문서나 Worker가 종료되어도 영속 작업 ID·확인된 part 목록에서 재개해야 한다.
- 선택한 실행 방식에서 느린 PUT, 대시보드 닫기, SW 종료·재시작 검사가 모두 통과해야 한다. 구현 전에 실행 위치를 짧게 검증하고 근거를 기록한다.

job에는 종류·버전·ID·export session ID·원격 폴더·확인한 part·단계·재시도 시각을 저장한다. 비밀값과 대형 본문을 job 메타데이터에 섞지 않는다. 기존 capture jobs와 별도 이름공간을 사용하여 런타임 복구가 백업을 웹페이지 캡처 작업으로 잘못 처리하지 않게 한다.

### 보관과 자동 삭제

- 첫 기본값은 자동 삭제 꺼짐이다.
- 사용자가 최근 N개/기간 보관을 선택한 경우에만 자동 정리를 켠다.
- 새 백업이 완전히 성공한 뒤 이전 **완료된** 백업을 정리한다.
- 마지막 정상본, 다른 기기 백업, OpenStill 밖의 자료를 삭제하지 않는다.
- 미완료 잔여 폴더는 작업 소유권과 재개 가능성을 확인한 뒤 별도 정리한다.
- 클라우드 용량이 부족하다고 이전 정상본부터 지우고 새 백업을 시도하지 않는다.

### Koofr 합성 서버/브라우저 검사

실제 계정 없이 먼저 로컬 WebDAV fixture 또는 제어 가능한 HTTP 모형으로 검사한다. 기대 결과는 저장된 원본·원격 파일·다시 복원한 자료를 비교한다. 구현 함수 호출 횟수만 확인하는 테스트로 끝내지 않는다.

- 등록 정보 없음 → 설정 버튼만 지정 위치에 표시, Koofr 전송 버튼 비표시
- 등록/수정/삭제 → 즉시 표시 상태 갱신, 새로고침 후 유지
- #runtimeOwnership 숨김 상태에서도 Koofr 설정 버튼 유지
- 401/403/429/507/5xx/네트워크 끊김/정상 207 및 항목별 실패 처리
- 첫/middle/last part 실패 후 기존 완료 세트 유지
- 원격 완료 목록 게시 전 종료 → 완료 목록에 나타나지 않음
- 같은 job 재시도 → 같은 part·백업 ID 사용, 중복 세트 생성 없음
- complete.json 또는 part 변조/경로 이탈 → 검증 실패, 자격정보 전송 범위 유지
- 목록의 악성 XML/파일명·잘못된 지문 → 안전한 파싱과 텍스트 표시
- 대시보드 닫기·새 Worker·SW 재시작·40초 이상 느린 업로드 → 작업의 완료 또는 명확한 재개
- 수동/예약 동시 실행·밀린 예약 여러 개 → 중복 실행 없음
- 복원 중 자동 백업 → 중간 상태를 정상 백업으로 게시하지 않음
- 같은 계정의 두 기기 → 서로의 폴더 덮어쓰기/자동 삭제 없음
- 비밀번호 변경/정보 삭제 → 후속 요청 중단, 백업 파일 보존
- 로컬·클라우드 JSON, job, 로그, UI 상태 응답에 비밀번호/Authorization이 없음
- 새 스크립트가 배포 ZIP에도 포함되어 실제 확장에서 실행 가능

### 실제 Koofr 호환 검사

최종 출시 전 별도 시험 계정/사용자가 지정한 시험 폴더로 다음을 확인한다. 자격정보를 채팅·저장소·로그에 남기지 않는다.

1. 무료 플랜에서 앱 비밀번호와 .json PUT/GET/PROPFIND/DELETE가 동작하는가.
2. 한글·이모지·HTML을 문자열로 포함한 실제 v5 JSON이 허용되는가.
3. 32MiB 미만 다중 part와 complete.json이 정상 동작하는가.
4. 새 임시 프로필에서 Koofr로부터 내려받아 전체 데이터가 복원되는가.
5. 느린 회선·연결 중단·재시도가 실제 서버에서도 동작하는가.
6. 자신이 만든 시험 파일만 정리하고 기존 원격 자료는 보존하는가.

실제 계정 검증을 하지 못하면 합성 검사 통과와 실제 서비스 미검증을 분리해 보고한다. 파일 형식 제한을 확인하지 않은 채 무료 계정 호환을 보장하지 않는다.

## 13. 실행 명령과 환경 인계

현재 환경에서 확인한 실행 경로다. 다른 계정/PC에서는 경로 존재 여부부터 확인한다. npm은 PATH에 없었지만 Node와 번들 Playwright는 있었다.

    node --test --test-reporter=spec tests/backup-integrity.test.js tests/recovery-json.test.js tests/service-worker-import.test.js tests/recovery-extensions.test.js

브라우저 검사:

    $env:OPENSTILL_PLAYWRIGHT_MODULE = 'C:\Users\chuum\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\node_modules\playwright'
    $env:OPENSTILL_CHROMIUM_EXECUTABLE = 'C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe'
    $env:OPENSTILL_EXTENSION_SMOKE = '1'
    node --test --test-concurrency=2 --test-reporter=tap tests/import-worker-browser.test.js tests/storage-browser.test.js tests/dashboard-browser.test.js tests/extension-browser.test.js

실제 백업이 제공된 경우에만:

    $env:OPENSTILL_SAMPLE_BACKUP = '실제로 제공된 백업 파일의 절대 경로'
    node --test --test-name-pattern='optional local backup' tests/service-worker-import.test.js

전체 최종 회귀:

    node --test --test-concurrency=2 tests/*.test.js
    git diff --check

실제 사용자 백업 선택 검사 환경변수가 남아 있으면 테스트 범위가 달라진다. 실행 전 지정 파일과 개인정보 출력 여부를 확인한다.

이미 통과한 비싼 검사를 조사 시작부터 반복하지 않는다. 수정 중에는 실패를 재현한 영향 범위 위주로 실행하고, 모든 구현을 마친 뒤 최종 회귀를 수행한다. 실패나 새 변경으로 근거가 달라진 경우에만 해당 검사를 다시 수행한다.

실제 확장 검사와 직접 전송·다운로드 fixture 검사는 구분한다. 기존 extension-browser는 실제 runtime 메시지 왕복을 검사하고, 모든 OS 다운로드 동작을 보장하는 검사는 아니다. 최종 추가 검사에서 실제 버튼으로 내려받은 JSON 파일을 새 프로필에 넣는 경로도 포함하면 좋다.

- 새 운영 모듈과 offscreen/Worker 파일의 package-release.ps1 포함 여부

버전 변경·ZIP 재생성은 실제 구현과 최종 검사 후 수행한다. 이번 계획서 작성 단계에서는 배포 파일을 재생성하거나 커밋/푸시하지 않는다. 이후에도 스토어 게시·외부 배포는 사용자의 요청 범위에 맞춰 처리한다.

최종 완료 조건:

- [ ] L1–L4의 재현 검사가 수정 후 기대 결과로 통과한다.
- [ ] 원본 내용·원본 지문을 손상 증거까지 포함해 보존한다.
- [ ] 반복/동시 가져오기가 원본을 덮어쓰거나 무한 중복을 만들지 않는다.
- [ ] 기존 로컬 백업·부분 복구·중단 재개가 유지된다.
- [ ] Koofr 설정 버튼과 조건부 전송 버튼이 사용자가 지정한 위치에 있다.
- [ ] Koofr 수동 백업·선택 복원·주기 자동 백업이 같은 v5 파이프라인을 사용한다.
- [ ] 느린 업로드·대시보드 닫기·SW 재시작에서도 데이터 보존과 재개가 검증된다.
- [ ] 비밀값이 백업·로그·일반 설정·원격 자료에 포함되지 않는다.
- [ ] 기본값에서 자동 실행·자동 삭제를 켜지 않는다.
- [ ] 기존 테스트와 신규 회귀를 최종 실행하고 pass/fail/skip 및 실제 서비스 검증 여부를 구분해 보고한다.
- [ ] 실제 사용자 데이터·개인 프로필·지정 폴더 밖 원격 자료를 건드리지 않는다.
